Critérios de Aceite em Formato BDD

CEN-L01: Campos Obrigatórios Vazios

400 Bad Request
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login sem fornecer email ou senha
    Dado que o cliente envia uma requisição POST para a API de login
    Quando o corpo da requisição for vazio
    Ou omitir o campo "email"
    Ou omitir o campo "password"
    Então a API deve responder com o código de status HTTP 400 Bad Request
    E o corpo da resposta deve conter na lista de mensagens: "Email e senha são obrigatórios"
Trecho do Código na API:
if (!email || !password) {
  return Response.json(
    { data: null, mensagens: ['Email e senha são obrigatórios'] },
    { status: 400 }
  );
}

CEN-L02: Formato de Email Inválido

400 Bad Request
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login com email em formato incorreto
    Dado que o cliente envia uma requisição POST para a API de login
    Quando o campo "email" for fornecido com formato inválido (ex: "joaosilva" ou "joao@silva")
    E a senha for informada
    Então a API deve responder com o código de status HTTP 400 Bad Request
    E o corpo da resposta deve conter na lista de mensagens: "Formato de email inválido. Use: nome@dominio.com"
Trecho do Código na API:
const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
if (!emailRegex.test(email.trim())) {
  return Response.json(
    { data: null, mensagens: ['Formato de email inválido. Use: nome@dominio.com'] },
    { status: 400 }
  );
}

CEN-L03: Senha Curta (< 6 caracteres)

400 Bad Request
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login com senha de comprimento menor do que o mínimo permitido
    Dado que o cliente envia uma requisição POST para a API de login
    Quando o campo "email" for fornecido em formato válido
    E o campo "password" contiver menos de 6 caracteres (ex: "12345")
    Então a API deve responder com o código de status HTTP 400 Bad Request
    E o corpo da resposta deve conter na lista de mensagens: "Senha deve ter pelo menos 6 caracteres"
Trecho do Código na API:
if (password.length < 6) {
  return Response.json(
    { data: null, mensagens: ['Senha deve ter pelo menos 6 caracteres'] },
    { status: 400 }
  );
}

CEN-L04: Usuário Não Cadastrado

404 Not Found
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login com e-mail não registrado no sistema
    Dado que o cliente envia uma requisição POST para a API de login
    Quando o email "naoexiste@exemplo.com" não estiver cadastrado no banco de dados
    E a senha for informada
    Então a API deve responder com o código de status HTTP 404 Not Found
    E o corpo da resposta deve conter na lista de mensagens: "Usuário não encontrado. Verifique o email ou cadastre-se."
Trecho do Código na API:
const { data: user, error } = await supabase
  .from('users')
  .select('id, email, password_hash, full_name, role, is_active')
  .eq('email', email)
  .single();

if (error || !user) {
  return Response.json(
    { data: null, mensagens: ['Usuário não encontrado. Verifique o email ou cadastre-se.'] },
    { status: 404 }
  );
}

CEN-L05: Conta de Usuário Inativa

403 Forbidden
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login por um usuário que possui a conta desativada
    Dado que existe um usuário cadastrado com e-mail "inativo@qatest.com"
    E a conta desse usuário possui a flag "is_active" definida como false
    Quando o usuário envia uma requisição POST de login com a senha correta
    Então a API deve responder com o código de status HTTP 403 Forbidden
    E o corpo da resposta deve conter na lista de mensagens: "Usuário inativo"
Trecho do Código na API:
if (!user.is_active) {
  return Response.json(
    { data: null, mensagens: ['Usuário inativo'] },
    { status: 403 }
  );
}

CEN-L06: Credenciais Inválidas / Senha Incorreta

401 Unauthorized
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Tentativa de login com senha incorreta para e-mail cadastrado
    Dado que existe um usuário cadastrado com e-mail "admin@qatest.com"
    Quando o cliente envia uma requisição POST de login informando este e-mail
    E preenche a senha com um valor incorreto
    Então a API deve responder com o código de status HTTP 401 Unauthorized
    E o corpo da resposta deve conter na lista de mensagens: "Email ou senha inválidos"
Trecho do Código na API:
const validPassword = await bcrypt.compare(password, user.password_hash);
if (!validPassword) {
  return Response.json(
    { data: null, mensagens: ['Email ou senha inválidos'] },
    { status: 401 }
  );
}

CEN-L07: Login Realizado com Sucesso

200 OK
Gherkin (BDD) 
Funcionalidade: Validação da API de Login

  Cenário: Autenticação de usuário com dados corretos e conta ativa
    Dado que o usuário está ativo e com cadastro válido no sistema (ex: "admin@qatest.com" / "Teste@123")
    Quando o cliente envia uma requisição POST com as credenciais corretas
    Então a API deve responder com o código de status HTTP 200 OK
    E o corpo da resposta deve conter o token JWT na chave "data.token"
    E a mensagem de retorno na chave "mensagens" deve ser: "Login realizado com sucesso"
Trecho do Código na API:
return Response.json({
  data: {
    token,
    user: { id: user.id, email: user.email, full_name: user.full_name, role: user.role }
  },
  mensagens: 'Login realizado com sucesso'
}, { status: 200 });

  Cenário: Falha crítica ou erro inesperado no backend da API

    Quando uma requisição POST de login for enviada
    Então a API deve responder com o código de status HTTP 500 Internal Server Error
    E o corpo da resposta deve conter na lista de mensagens: "Erro interno do servidor"
Trecho do Código na API:
} catch (error) {
  console.error('Erro no login:', error);
  return Response.json(
    { data: null, mensagens: ['Erro interno do servidor'] },
    { status: 500 }
  );
}
